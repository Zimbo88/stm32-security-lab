# STM32 Security Lab v1.0.1

## Summary

Version 1.0.1 is the first hardware-validated secure-update release intended
for public Open Source review.

This release is superseded by v1.0.2, which keeps the code and security formats
unchanged and clarifies which release packages are default version-2
provisioning artifacts versus higher-version positive update-test artifacts.

It keeps the signed-image and update-package formats unchanged while publishing
the completed EXP045/EXP066 secure-boot and dual-slot update path, updated
documentation, release guidance, deterministic-build evidence, and CI fixes.

## Highlights

- Stage-0 secure boot for STM32F429 with SHA-512 payload verification.
- Ed25519 authentication over the canonical signed manifest.
- Redundant boot metadata with `WRITING`, `CANDIDATE_READY`, `PENDING_TRIAL`,
  `CONFIRMED`, and `REJECTED_INVALID` lifecycle states.
- Slot A/Slot B boot selection, trial boot, application confirmation, rollback
  rejection, and fallback behavior.
- Streaming secure-update installer with fixed RAM buffers and no dynamic
  allocation.
- USART1 polling RX/TX transport and deterministic `SUPD` UART binary protocol.
- `stm32ctl` host tool for local package verification, status, update, and
  reset.
- Read-only bootloader diagnostic console.
- EXP066 Runtime Security Monitor foundation and LED4-only running heartbeat.
- Deterministic build comparison and private-key scan in local checks and CI.

## Hardware Validation

The v1.0.1 evidence was collected on an STM32F429IGT6-class board at RDP Level
0 with ST-LINK and USART1 attached.

Validated on real hardware:

- confirmed Slot A boot with SHA-512 and Ed25519 executed before jump;
- A-to-B authenticated update to Slot B version 3;
- Slot B trial boot and application confirmation;
- B-to-A authenticated update to Slot A version 4;
- Slot A trial boot and application confirmation;
- rollback rejection for same and lower image versions;
- fail-closed rejection of corrupted manifest, target, signature, and payload
  cases;
- abort and reset during `WRITING` preserving the confirmed fallback slot;
- UART CRC, sequence, partial-frame, and random-byte negative cases;
- byte-for-byte flash readback for both positive update targets;
- unchanged RDP0 Option Bytes during the campaign.

The previous A-to-B timeout was traced to hardware timing: `BEGIN_UPDATE`
performs inactive-slot erase before ACK and took about 6.3 seconds on the test
board. The host default response timeout is now documented and configured for
that measured behavior.

## Host Validation

Host tests cover Python tooling, update-package build/verify/inspect paths,
stm32ctl behavior, C verifier boundaries, update metadata, update protocol,
UART polling, diagnostic console, RSM core logic, sanitizer variants where
supported, deterministic-build comparison, repository audit, and tracked-file
private-key scanning.

## Security Boundaries

The release does not approve:

- RDP1 or RDP2 provisioning;
- Option Byte, WRP, OTP, or irreversible hardware configuration changes;
- production signing-key custody, rotation, or revocation;
- hardware-backed monotonic rollback counters;
- physical recovery input;
- certified fault-injection, glitch, or side-channel resistance;
- production remote-update authorization beyond signed firmware packages and
  rollback policy.

Physical power-removal timing and visual LED observations should be repeated
for each board and power setup before any irreversible protection planning.

## Release Artifacts

Expected release artifacts are built from the tagged commit:

- EXP045 bootloader ELF/BIN/HEX and size report;
- EXP066 Slot A and Slot B ELF/BIN/HEX;
- Slot A and Slot B signed update packages;
- package inspection and verification JSON reports;
- SHA-256 checksum file;
- release notes and validation documentation.

Private signing seeds and private keys must never be included in release
artifacts.
